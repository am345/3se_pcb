# 板卡工作流程

## 新增板子

1. 确定稳定的 `board-id`，如 `serialleg-logger`。用小写英文和连字符，不使用日期、“最终版”或日常修订号。
2. 创建 `boards/<board-id>/hardware/`，把 [README 模板](../templates/board-readme.md)复制成 `boards/<board-id>/README.md`，填写实际情况。
3. 用 EDA 创建完整原生工程；不要提交伪造的空工程入口。只创建实际需要的文档、图片与机械目录。
4. 在板 README 写明工程入口、软件版本、供电与接口，以及当前未确定的条件。
5. 更新[根索引](../README.md)，提交本板工程与文档。

## 迁移已有工程

- 保存工程，必要时关闭编辑器，使数据库或磁盘文件处于一致状态。先复制，原副本保留。
- `.eprj3` 连同原理图、PCB、配置及关联库资源一起复制；KiCad 连同符号、封装、模型与库表一起复制，消除个人绝对路径依赖。
- `.eprj2` / `.epro2` 可以先作为原始工程导入 Git，不要通过改扩展名“转换”。需要文本版本管理时用支持该格式的 EDA 导出/另存，再核对。
- 明确迁移后唯一维护入口，避免原副本和仓库副本同时修改；旧报告和截图注明来源及时间。
- 在新位置打开工程，检查缺失库、器件数、连接关系和必要资源。未完成重开验证时，必须保留为待验证事项。
- 原始设计资料与第三方来源说明一并保留。其他板子的来源位置尚未明确时，不把机器上不相关的工程自动纳入。

## 日常修改

1. 检查工作区差异，阅读目标板 README 的状态和已知问题。
2. 一个分支处理一项明确任务；同时改多块板时写清影响。
3. 按 [AGENTS.md](../AGENTS.md) 设计和检查；禁止自动布线。
4. 保存工程并查看 Git diff。原生 EDA 文本合并后仍须重开工程，不能把文本无冲突当成电气正确。
5. 更新对应说明和预览。保留的检查报告写清适用版本，临时文件放 `outputs/`。
6. 提交本任务的源文件、相关说明和必要验证证据；不夹带其他工作。

## 投板与版本归档

设计状态：

| 状态 | 含义 |
| --- | --- |
| 设计中 | 电路、布局、布线或检查仍有未完成项 |
| 待投板 | 对应版本的设计及制造检查已完成，尚未送厂 |
| 已投板 | 已有实际送厂记录，样板可能尚未验证 |
| 已验证 | 有注明条件、范围和结果的样板实测记录 |
| 停用 | 不再维护，保留旧版本与原因 |

正式生产文件从确定的源提交生成，并记录 EDA 版本、制造层叠/工艺、装配变体和 DNP 清单。每个生产包都必须包含或明确说明：

- Gerber 与钻孔文件；
- 生产 BOM 与贴片坐标（不贴片时注明不适用）；
- 原理图 PDF；
- 制造/装配说明及必要的检查证据。

可将文件导出到 `boards/<board-id>/outputs/<version>/`，送厂前核对内容。不要仅凭导出成功创建可生产结论。

标签示例为 `serialleg-logger/r1.0`，在板 README 中记录该版本及对应设计变更。

已投板版本的源标签固定。任何影响生产的变化都使用新版本；若发现旧版本有问题，在板 README 中补充问题与替代版本。

## 大文件与共用资源

- 日常生成的生产 ZIP 放 `outputs/`，不反复提交到源历史。
- 必需的大型 STEP、机械装配等文件达到实际管理瓶颈时，再单独评估 Git LFS；不要一开始把全部 EDA 文本文件转成 LFS。
- `libraries/` 只用于确实共享的库。共用库更新须检查引用它的板子，发布标签保留相应历史。
- 固件已有独立仓库时，在板 README 记录链接、硬件兼容范围与对应 tag/commit。
- 只服务于单块板的板载固件放 `boards/<board-id>/firmware/`。从外部导入时先在原仓库提交未完成的改动，用 `git bundle` 把历史打包放到板 `docs/firmware-history/`，再复制不含 `.git` 的文件树；用两边的文件 blob 对比确认内容一致。
